## 1. 建议采用的整合范围

**以 v9 统一准入和候选排序，沿用现有资金与集中度约束，分别冻结选品、配置、收益测算和评估版本。** 新策略生成的新决策使用新评估规则；历史决策保留原策略、原预测和原评价依据。当前持仓则无论购入时采用何种策略，都接受当前有效策略的持续监控。

本轮建议完成以下闭环：

> 初筛公开证据 → 同份额映射与时效校验 → 新策略配置建议 → 交易前复核 → 提案/决策 → 用户银行交易 → 截图与确认事实 → 分版本评估与复盘。

v9 没有规定完整的资金分配算法，不能把初筛前三名直接当作组合。它也没有把近 1 月年化定义为个人未来收益预测。因此，本轮同时统一输入和判定职责，不把所有收益指标替换成近 1 月年化。

`TD-R2-ALLOC-001` 的取消固定分桶、资金日历和跨桶机会成本方案已于 2026-11-05 暂缓。本轮不默认恢复该方案。先完成 v9 与现行配置框架的整合；若以后启用动态配置，应以独立配置版本替换本计划的配置层，不重做初筛和历史审计链。

## 3. 统一后的策略契约

### 3.1 v9 准入与排序

直接复用 `server/modules/r2-screening/policy.js` 及其证据计算，避免在配置、持仓和评估模块各写一份阈值。原始口径以 [初筛 v9](r2-product-screening-strategy.md) 为准。

| 项目 | 整合口径 |
| --- | --- |
| 适用范围 | 人民币、公募、已验证 R2/PR2；按同一销售份额和渠道取证 |
| 近 1 月年化 | 最新有效官方值必须 ≥2.15%；低于门槛禁止新买、加仓、续持；缺失、过期、错配为待核 |
| 期限 | 锁定期限上限 190 天，定开排除，滚动持有待核；未知期限可以保留初筛提示，但不能直接生成确定金额的可执行建议 |
| 最大回撤 | <1% 为正式资格；1%–1.5%（含两端）仅观察；>1.5% 淘汰；观察、待核和淘汰均不用于新增自动配置 |
| 挂零、走势 | 按 v9 原始净值精度与日历计算，仅提示，不额外扣分、淘汰或偷偷改变排序 |
| 候选顺序 | 公开产品分类和实际公开期限相同的组内，按近 1 月年化降序；同分沿用渠道、代码稳定排序 |
| 正式名单与替补 | 每组前 3 名保持研究展示；分配时可继续使用组内其他通过份额，保留原排名及启用替补原因 |
| 公开可买状态 | 新买要求 `quota_status=0`；`1` 为售罄，未知不放行。该字段不是已持仓的续持或退出条件 |
| 公开金额 | 有金额按原值约束；状态 0 且金额空白按用户规则“大于 5,000 万元可买”测算，另存假设来源；不伪装为银行披露，不设明确金额优先 |
| 数据有效期 | 近 1 月业绩和最新有效净值分别按实际数据日判断；距决策日达到 7 个自然日即待核；重新抓取相同日期不续期 |

### 3.2 本轮保留的组合约束

- 应急金在组合外；日开新增目标和计划现金目标均为 0%；3% 保留为进取目标及差距展示，不作为 v9 选品硬门槛。
- 短/中/长仍按 1–30、31–100、101+ 天分类；v9 新增候选再受 190 天上限约束。已有超长期或日开持仓继续作为事实显示。
- 沿用短 30% / 中 35% / 长 35% 的配置目标，单产品上限 30%；6M 和仅 3M 档分别单只 10%、同档合计 20%；只有 1M 的新品保留人工观察，不因通过 v9 就自动获得金额。
- 短期流动性下限及既有用款约束继续生效，统一“评分短桶”与“7–30 天流动性子集”的计算口径。取消下限或改用精确资金日历应另纳入动态配置方案。
- 底层策略集中度按当前已核验口径统一；v9 接入不得顺带放宽。旧实现对单一策略族存在特殊处理，阶段 0 必须对照正式规则登记，而不能直接复制为新策略默认。发行方占比只展示。
- 现有持仓、待确认买入和切换承诺金额都占用额度。集中度以统一组合本金及交易后的组合敞口计算，不以某张提案金额作分母。

**满仓是配置目标和成功验收条件，不能靠使用不合格产品或隐去资金缺口实现。** 按 v9 排名扩展替补、补足已选份额后，若仍不能同时满足资金、额度、集中度及流动性约束，返回“无可行满仓方案”、缺口金额及冲突约束，不输出“全部达标”。

2026-11-07 的量化比较曾出现 v9 满仓后短桶仅 20% 的结果；它说明当时约束存在冲突，不构成把生产流动性下限自动改为 20% 的授权。本轮应明确展示该冲突，不能照搬分析脚本的跨桶补配策略。

### 3.3 收益指标各司其职

| 指标 | 用途 | 不可混用的地方 |
| --- | --- | --- |
| 近 1 月年化 | v9 门槛、同类同期限候选排序、当前续持监控 | 不直接作为未来收益承诺，不代替个人已实现收益 |
| `reference_yield_pct` / `r2-term-yield-v1` | 配置参考年化、3% 差距、费用与空档测算的情景输入 | 不再据此覆盖 v9 排名，不覆盖近 1 月门槛 |
| 旧 `selection_score` | 历史复算、旧策略观察与对照 | 新策略页面不得再将其标成当前推荐排名 |
| 交易后产品收益事实 | 结果评价、归因、预测校准 | 只使用确认持仓及收益事实，不把公开净值当作个人收益写账 |

继续使用原收益公式、缺失窗口语义和舍入规则，不修改既定权重。v9 合格但参考年化不可计算的份额仍可展示初筛结论；净收益比较和自动金额保持待核，不填 0 或用别的份额替代。

## 4. 数据来源、份额映射与版本冻结

### 4.1 读取链路

保留独立初筛库及账本库。新增决策证据适配层，建议位于 `server/modules/products/` 或独立策略 service，通过接口注入初筛 repository；不得让 `lib/products.js` 直接打开生产库或自行联网。

保持模块化单体：`server/app.js` 负责依赖装配，新增 HTTP 用例在 `server/http/routes.js` 登记；route 处理输入输出，service 负责用例及事务，repository/adapter 负责 SQL 与外部来源。持仓补采复用现有生命周期与公开客户端，不新增独立守护进程。

1. 读取已发布批次并冻结 `run_id`。只接受可发布的 `succeeded/degraded` 结果，运行中或失败批次不替换最后成功发布结果。
2. 将该批次证据适配为候选、已持仓监控和交易前复核三个视图，逐项按当前北京时间重新判断时效。
3. 一次配置计算、提案生成及相关页面投影使用同一个冻结批次，不在循环里反复查询 current 指针。
4. 提案/决策保存其使用的证据摘要、哈希、版本和时间。初筛 current 指针更新不改写已有快照。
5. 普通 GET 只读取；手动初筛、周快照、复核确认、提案生成分别由明确的写用例负责。网络请求在账本事务外完成。

`degraded` 不一律整批禁用，也不一律视为健康。逐份额检查必需证据完整性、同份额匹配和时效；全局缺页、日历不足或来源身份异常等无法证明候选完整性的故障，应阻止自动分配并说明原因。局部缺失仅隔离相关份额。

### 4.2 映射规则

身份使用 `(source, channel, sales_code)`，辅以登记编码、份额名称和核验依据。现有仅按产品代码存储的持仓/设置，通过明确的一对一映射连接，不按相似名称补配。登记编码用于识别同产品多份额敞口，不能把不同份额的收益或额度相互代用。

无映射、多渠道歧义、登记信息冲突时，保留持仓事实并标记待核，阻止该份额新增可执行建议。原始代码和历史交易不得为适配新键而重写。若现有集中度使用代理键，显示代理依据和局限，不能声称已经完成资产穿透。

### 4.3 分层版本和快照

建议新增执行策略标识 `r2-screening-v9-execution-v1`；最终命名在实施阶段 0 冻结。它引用独立的 `selection_policy_version=v9`、配置版本、`yield_policy_version=r2-term-yield-v1`、持仓复核版本和评估版本，不复用旧 `r2-3pct-v1` 名称冒充升级。

最小审计字段应包括：

- 策略及各子版本、决策模式、策略契约哈希、生成时间与业务日期。
- 初筛批次、来源/渠道/销售份额、登记映射、组别与组内原始排名。
- 1M/3M/6M/1Y 及各数据日，参考年化状态、原因、可用窗口和归一化权重。
- 净值观察区间、净值证据哈希、回撤与修复、挂零与走势提示、准入及拒绝原因。
- 公开额度状态/查询时间/金额原文、金额策略假设、App 复核事实及复核时间，彼此分开。
- 配置本金、已有/待确认敞口、集中度分母、各约束与未配金额、持仓批次及交易腿。
- 正式期限、申赎截止/确认/到账依据、最早资金可用日；资产条款、报告期、核验人、来源和证据哈希。
- 比较期、收益情景、费用、资金空档、冻结预测、证据日、验证日及失效条件。

优先复用现有提案 payload、决策 `review_meta`、评估证据等 JSON 扩展字段，保持路径和既有响应字段兼容。新增字段不能只藏在前端状态中。历史缺失字段标为“历史未冻结”，不拿最新证据补成当时已经通过。

初筛库只保存公开事实；不把账户本金、持仓、用户用款或交易截图写入其中。账本业务事务仅持久化本次决策必需的证据副本，不使用跨库写事务或复制整库。证据副本必须足以在初筛库离线时解释原决策。

## 5. 产品配置改造

### 5.1 从旧评分池切换为 v9 候选输入

将旧产品快照装饰、收益公式和配置算法解耦。新策略候选必须来自冻结 v9 结果，不能再先经过旧 `selection_score` 门槛，也不能要求候选已存在于周 CSV 中。周快照保留查询、旧策略复算及样本观察用途。

新增配置先检查 v9 资格，再检查自动配置的证据档位、期限与分类可识别性、起购/递增金额、公开状态、账户限制、资金和组合约束。已有持仓优先的旧排序不再覆盖 v9 收益顺序；需要避免碎仓时，通过明确金额约束说明跳过原因。

先按现行期限桶预算分配；桶内保留 v9 的“分类＋实际期限”组别。不同分类或不同实际期限之间没有 v9 授权的总排名：建议沿用现有预算，默认对组首轮均衡分配，再按预先冻结的组间顺序分轮补足，不把跨组近 1 月最高视为唯一分配依据。组间预算与顺序作为配置规则单独验收。

前 3 名只是研究展示上限。名额不足、集中度已满、起购不符或额度不足时，按原组排名继续找通过份额；使用替补、补仓及未能用满的每个金额都必须可解释。明确金额和空白金额不建立优先级差异。

### 5.2 三层状态

| 状态 | 可做什么 | 还缺什么 |
| --- | --- | --- |
| 公开初筛通过 | 展示研究顺序、进入配置试算 | 可能仍缺正式期限、账户可买和资产复核 |
| 配置试算通过 | 展示建议金额、收益情景与约束结果，可保存待核草稿 | 交易前清单未完成时不能展示为可执行指令 |
| 交易前复核通过 | 形成明确金额的待用户执行提案；采纳前再校验失效条件 | 实际交易仍由用户在银行完成，之后补截图及确认事实 |

复核覆盖 v9 规定的正式持有期与到账路径、App 实际销售限制、说明书允许资产、最新报告实际资产、权益上限及禁入暴露。资产/久期没有结构化公开字段时，提供人工证据录入和待核状态，不能用“有 PDF 链接”代替“已读并核验”。

## 6. 持仓复核、续持与退出

### 6.1 先判断能否续持，再判断有没有更优替代

| 当前证据与持仓状态 | 新策略结论 | 后续处理 |
| --- | --- | --- |
| 有效近 1 月年化 <2.15%，当前可赎 | 不符合续持，建议按实际路径退出 | 形成赎回或有合格去向的切换提案；无替代品也保留退出结论 |
| 有效近 1 月年化 <2.15%，仍锁定 | 不符合续持，最早可赎日退出计划 | 显示“锁定中，待开放退出”；动作保持观察并保存退出意图，不写成可立即切换 |
| 收益缺失、过期或份额错配 | 续持判断待核 | 禁止新买/加仓；发起证据复核，不把缺失当低于门槛，也不自动认可续作 |
| 收益达标，只有公开售罄或未进前三 | 不单凭此触发退出 | 继续按持仓风险、条款、净收益和可赎状态复核 |
| 回撤进入观察或淘汰区、期限/资产条件不符 | 当前策略风险复核 | 停止新增自动配置；独立标明续持/退出依据，不把“新买淘汰”直接推成已成交赎回 |
| 达标且续持条件未见失效，替换经济性不足 | 继续持有 | 给出下次验证日期和失效条件 |

“低于 2.15% 退出”是 v9 明确的持续规则，优先于旧系统默认到期续作，也不受可选换仓的利差和增益门槛阻挡。退出费用、到账和空档仍需显示，但不能因此把不合格产品标成符合续持。

其他初筛条件用于存量持仓退出的边界，需在阶段 0 明确登记；v9 未明确的强制退出条件不可凭实现方便推导。尤其公开售罄不是赎回状态，190 天上限也不允许系统假设旧锁定持仓可以提前退出。

### 6.2 覆盖全部持仓

不能直接把初筛 `rejected` 当成持仓退出结论。当前采集优先补齐收益达标且公开可买份额的详情和净值；持仓即使售罄、下架或未达收益门槛，仍要按批次取得所需公开证据和已核验申赎规则。

新增持仓监控证据补采入口或采集模式，复用公开客户端，对没有新增候选资格的存量份额仍可取证。公开请求仅携带产品身份，不发送账户金额；持仓监控结果不反向把售罄份额加入新买名单。来源不可用时显示最近证据和待核项。

### 6.3 自愿换仓继续计算经济性

当前持仓仍合格时，替换候选改用 v9 合格集合，保留现有复利切换计算及最低条件：参考年化优势 ≥0.15pp、扣费和空档后增益 ≥`max(1 元, 本金×0.10%×比较天数/90)`、候选高于盈亏平衡年化 0.05pp。

同本金、同明确比较截止日展示持有与切换情景。沿用的 30/100/360 天比较期属于测算情景，不是产品可锁定期限；候选自身仍受 190 天上限。需要滚动续作时披露再投资假设，不能默认未来每次都有额度且保持当前收益。

锁定中的优选候选只形成到期后观察计划；到达窗口后重新验证候选及收益，而非自动把旧计划变成交易。

## 7. 提案、手工决策与交易审计

### 7.1 统一入口

自动配置、持仓切换、强制续持门槛退出、手工决策都从同一策略契约取得默认版本与规则。移除新记录路径上的旧策略硬编码；历史编辑仍按原策略解释。前端选择策略不能绕过后端的证据和版本校验。

现有动作只有“买入/赎回/切换/观察”，首版可保留，通过计划动作字段区分“到期退出”“到期替换”“复核续持”，不为记录计划伪造交易。理由、预期、证据日、验证日、失效条件及原始交易截图链继续必需。

提案去重键加入执行策略契约版本、批次/证据指纹、持仓 lot 或产品身份、金额及交易腿。同一输入重复计算不重复生成；新批次但经济结论未变时，按明确的替代规则关联前版，避免每日制造重复待办。旧决策不能仅因产品代码相同，就永久阻止新批次风险退出或新的持仓复核。

### 7.2 状态切换

| 对象状态 | 切换处理 |
| --- | --- |
| 旧版待采纳提案 | 通过明确写用例作废，记录选品/执行策略升级原因；不得复用旧预测再贴新摘要 |
| 旧版已采纳、未执行 | 决策原文和预测保留；标记需按当前策略复核、暂停继续推荐，生成关联的新复核记录 |
| 部分执行 | 已成交金额保留原策略和证据；仅对未执行余额重算，不能重复占用或把整单作废 |
| 已执行、已完成或已有绑定交易 | 保留原策略、交易绑定和历史评价；新增当前持仓监控结果，不原地改策略 |
| 新版待采纳、证据过期/状态变更 | 停止采纳，说明具体失效项，重新取证后生成新版本 |

采纳时校验当前激活策略、证据时效、公开状态及用户复核、资金/待确认承诺、集中度和交易腿。请求中的旧 `run_id` 不能绕过当前失效状态；不能只校验收益公式版本。必要的源刷新在事务外完成；持久化校验与采纳在账本事务内完成，并校验冻结上下文未被新资金状态替换。

账户无法联网核验时，允许保留带条件的草稿，不自动放行。批次更新但证据未变时，按确定规则重新确认上下文；批次/关键状态竞争导致无法证明一致时，拒绝采纳并要求重算。

**实际交易事实必须允许如实入账。** 用户已在银行执行旧计划或不合规交易时，继续要求合法决策绑定和原始截图，记录偏差及复核事项；不得因为当前 v9 不通过而丢弃真实资金事实，也不能把它包装成新策略合规交易。新建未来推荐与补记已发生事实应有明确入口语义。

## 8. 自动评估与预测校准

### 8.1 新旧规则分发

评估器按决策冻结的策略契约和评估版本分发，不再以当前全局设置替换历史规则。新策略决策必须保存完整评估参数；旧记录能证明的按原快照复算，不能证明的标记历史证据不足。新持仓监控使用当前策略，和“当时决策是否合规”分别展示。

| 评估类型 | 新策略应检查什么 |
| --- | --- |
| 决策/交易流程 | 当时 v9 证据与排名、交易前复核、条款、组合约束、决策/截图绑定、实际执行偏差 |
| 持续监控 | 当前 1M 是否低于 2.15%、证据是否过期、风险变化、实际可赎日及退出计划 |
| 结果评价 | 冻结预测与个人实际收益/净增益，扣费、空档和明确比较期；证据不足进入待确认 |
| 组合目标 | 独立展示距离 3% 的差距及期限结构，不把目标未达直接判为 v9 选品流程错误 |

旧短/中/长 2.5%/2.8%/3.0% hurdle 保留用于旧策略历史评价；新策略不自动继承这些门槛作为流程否决条件。新结果按已冻结的可检验预测评估，3% 作为目标另列。2.15% 是公开近期业绩的续持门槛，不是个人已实现年化的达标线。

买入流程集中度、证据档位总上限、流动性等应使用该次交易后的整体组合快照，避免单产品提案因占本决策 100% 而被误判超单只 30%。新策略各模块对分母、待确认交易占用、取消交易释放和在途赎回的处理必须一致。

### 8.2 实际收益与校准边界

保留 `product_daily_valuations` 为唯一收益事实源、`daily_records` 为逐日投影；个人持有起点使用确认日。新策略不能通过导入公开历史净值“补齐”个人收益，也不能为了评分填补缺失的 0 元收益。

未采纳、未执行、已失效、未到验证日或证据不足的预测不计命中率；旧、新策略及不同预测指标分开展示样本量与结果。规则退出后未实际卖出的持仓，也不能假设已经取得退出收益。

## 9. 页面与消息整合

### 9.1 已确认的信息架构

用户已确认合并初筛和配置入口。侧栏将“产品与配置”“选品初筛”收敛为一个“选品与配置”，页面内部按任务分区；“决策与评估”承接方案的处理和结果。采用现有 Vue、主题变量和组件体系，遵循工作区既有的专业金融终端与现代 SaaS 工作台方向，优先对齐数据、减少卡片嵌套，不另起一套视觉系统。

| 一级入口 | 主要分区 | 页面负责回答的问题 |
| --- | --- | --- |
| 选品与配置 | 候选初筛 / 资金配置 / 持仓复核 | 现在有哪些合格产品？资金怎么安排？现有持仓该继续、待核还是退出？ |
| 决策与评估 | 待处理提案 / 决策记录 / 评估与校准 | 哪份方案需要处理？当时为何决定？实际执行和结果如何？ |
| 交易与持仓 | 保留现有持仓、收益事实、流水和截图收件箱 | 银行实际发生了什么？证据和确认状态是什么？ |
| 消息中心 | 跨模块需处理事项 | 现在需要补什么事实或确认什么决定？ |
| 复盘 | 保留周期总结与验证结论 | 哪些规则和预期值得修正？ |

持仓事实继续以“交易与持仓”为准，“选品与配置”的持仓页只负责策略复核；正式提案和决策记录只有一份，在“决策与评估”处理。“选品与配置”可以显示关联提案状态和定位链接，不另建一套采纳记录。

### 9.2 路由、导航与旧链接兼容

建议保留 `/ledger/products` 作为合并工作区，一级分区用 `section` 标识。`tab` 继续保留给初筛内部筛选，避免与已有查询参数冲突。下表为实施时需冻结并测试的路由契约。

| 目标 | 新入口或兼容规则 |
| --- | --- |
| 侧栏“选品与配置” | `/ledger/products?section=screening`，从候选初筛进入；当前侧栏只选中一个入口 |
| 资金配置 | `/ledger/products?section=allocation`；原无查询参数的 `/ledger/products` 继续解释为配置，兼容既有书签 |
| 持仓复核 | `/ledger/products?section=holdings`，可携带产品身份和 `lot`；收益排行为其内部 `view=performance` |
| 原初筛链接 | `/ledger/screening?...` 映射到合并工作区的初筛分区，保留 `run/tab/channel/code/page/term/category/issuer/hint/q/stage/sort/log` 等有效原参数 |
| 原持仓定位 | 原 `#holding-reviews`、`?view=performance#holding-reviews` 映射到持仓分区及对应查看方式；原 `#events` 定位持仓分区内产品事件 |
| 待处理提案 | `/ledger/evaluation?section=proposals`，支持按提案 ID 定位，区分待采纳、待执行、部分执行、需重核 |
| 决策记录 | `/ledger/evaluation?section=decisions`，支持按决策 ID 定位及策略/日期筛选 |
| 评估与校准 | `/ledger/evaluation?section=results&view=evaluations` 或 `view=calibration`；原 `#automation`、`#calibration` 自动选择对应分区 |
| 原提案/决策锚点 | `#proposals`、`#decisions` 保留定位语义；消息中心和其他页面的旧深链继续可用 |

显式 `section` 优先于旧锚点推断；无效参数回到合理的只读默认分区并给出提示。路由规范化使用替换历史记录，用户主动切页签进入浏览器历史；后退应恢复分区、筛选、列表页码、详情与滚动位置。

工作区一级分区使用路由导航，初筛的“正式候选/全部份额/观察/待核/淘汰”降为该分区内的筛选控件；“评估与校准”内部切换评价与统计。避免同时保留旧页内目录、一级页签和多行胶囊来表达同一层级。

详情上下文应包含来源/渠道/销售代码、批次以及必要的 lot/提案/决策 ID。URL 不携带账户金额、截图路径或完整证据对象。定位对象不存在、已失效或无权读取时显示具体原因，不打开同名产品顶替。

### 9.3 各分区的内容与动作

| 分区 | 首屏主要信息 | 主操作与后续 |
| --- | --- | --- |
| 候选初筛 | 当前/历史批次与数据日、来源健康摘要、同分类同实际期限的候选表 | “刷新初筛”；行内“查看证据”“加入配置试算”。历史批次只读，切回当前证据后才能进入正式配置 |
| 资金配置 | 可分配金额、待确认占用、本次配置/未配金额、期限结构及冲突原因 | “重算配置”；试算行进入“完成交易前复核”，满足条件后“生成待采纳提案”并定位正式提案 |
| 持仓复核 | 待核、续持不达标、待开放退出、可替换的持仓批次，优先展示需要处理者 | 行内“补齐证据”“查看退出计划”“比较替换”；收益排行和产品事件作为该分区内的次级视图 |
| 待处理提案 | 提案原因、金额、证据日、有效期、当前动作及阻碍项 | 待核先复核，合格后“采纳，待我执行”；已采纳后进入关联截图入口，不把采纳表述为交易完成 |
| 决策记录 | 策略、理由、冻结预期、实际执行状态、下一验证日 | 查看证据与评估；手工新建默认当前策略，历史更正遵循绑定冻结规则 |
| 评估与校准 | 待确认评估、流程评价、结果评价、按策略分组的预测样本 | “补齐评估证据”“确认评价”；完整历史和自动化设置按需展开 |

产品表优先列名称/销售代码、期限及分类、近 1 月年化/数据日、回撤、组内排名与准入状态；参考年化明确标注为测算指标。配置表增加建议金额、额度依据和阻碍项；持仓表增加批次、续持结论与最早可赎/到账日。详细窗口、净值点、费用和版本放在详情，避免把所有字段挤在同一宽表。

“刷新初筛”只刷新公开证据；“重算配置”读取当前已发布证据和账户状态；“查看周快照/刷新周快照”归入次级数据工具，用于查询及旧观察，不与当前 v9 候选并列为两个推荐池。“重新评估”只触发评估用例，不顺带刷新产品或自动采纳提案。

试算允许调整纳入范围，但必须展示筛选对结果的影响并保留 v9 原排名；用户勾选不能使不合格产品获得资格。提交前检查全部资金约束，不能因为只查看某页产品而误将当前页当作全量候选。

### 9.4 页面结构与共享详情

统一采用“页名与当前结论 → 分区导航 → 必要摘要/阻碍项 → 主表或任务列表 → 按需证据详情”的结构。一个分区保留一个明确主动作，批次健康摘要不复制为每页多张指标卡；详细错误集中展示，相关行保留原因入口。

结构示意用于约定层级，不是已经实现或验收的界面：

```text
选品与配置                         初筛 v9 · 证据日期/批次
候选初筛       资金配置       持仓复核
------------------------------------------------------
当前结论与阻碍项                       当前分区的主操作
筛选条件 / 配置摘要 / 持仓处理分类（随分区变化）
产品或批次 | 关键指标 | 结论与原因 | 下一步
------------------------------------------------------
证据详情按需打开；配置金额汇总与提交区仅在配置时出现
```

以已有 `ScreeningDetail.vue`、`ProductDetailDialog.vue` 的能力为基础，提取可复用的产品证据内容：判定与排名、收益与净值、条款及资产、交易前复核。公共外壳统一产品身份、数据日、关闭和返回；不同来源内容保留各自适用范围，旧周快照不能显示成 v9 已核验。

优先行内展开和页内详情；需要跨表对照时使用单个侧向详情面板。交易前核验表单在同一详情区域逐项填写，不层层弹出模态框。只对采纳、拒绝、取消采纳和危险修改提供一次明确确认，复用现有确认组件。

草稿编辑期间证据更新时显示“有新批次可用”，不自动替换本次快照、金额或已输入理由；用户重算或提交时校验新状态。关闭或跨页时保留本地草稿或明确询问是否放弃，不能把关闭视为保存。

### 9.5 四条贯通流程

1. **新资金配置。** 候选初筛看组内排序 → 加入配置试算 → 查看金额和约束 → 完成交易前复核 → 生成提案 → 在决策区核对并采纳 → 银行执行 → 携带决策上下文上传截图 → 交易确认后查看评估。进入试算不写交易、不改原候选排名。
2. **存量不达标。** 概览/消息进入具体 lot → 显示低于 2.15% 的证据和可赎状态 → 可赎时准备退出提案，锁定时记录待开放退出计划 → 到窗口重新核验 → 银行执行及截图。无替代产品时仍可形成退出结论，不强迫先选新产品。
3. **历史与偏差复核。** 决策记录进入原提案/预测 → 查看实际交易和评估 → 区分原策略合规、当前持仓监控及执行偏差。需要改计划时新建关联决策，不直接改写已绑定记录。
4. **局部数据故障。** 账本不可用时仍能看公开初筛；初筛不可用时仍能看持仓和历史决策事实。缺失数据只阻止依赖它的当前推荐或提交，页面明确指出缺口及重试入口。

“上传成交截图”应携带决策/提案上下文并在收件箱核对；用户仍可补记已发生的计划外交易，并明确记录偏差。采纳后的进度为“待银行执行 → 已提交截图/待校正 → 待确认 → 已确认”，以实际返回状态为准，不能靠按钮点击本地推断完成。

### 9.6 状态、反馈与防误操作

分别展示三类状态：产品准入、证据时效、决策执行。例：“初筛通过 · 正式期限待核 · 暂不能生成可执行提案”，不能用一个绿色“通过”覆盖所有条件。

| 情形 | 页面反馈与允许动作 |
| --- | --- |
| 通过但挂零/走势提示 | 保留通过与原排名，同时显示人工复核提示 |
| 续持不达标且锁定 | 显示“续持不达标 · 锁定至某日/可赎日待核”，查看退出计划，不显示普通“继续持有” |
| 数据过期或新方案失效 | 保留原证据可查，说明哪项过期；禁止采纳，提供更新证据/重算入口 |
| 无候选 / 筛选无匹配 / 未初始化 | 分别显示原因和对应行动；清筛选不能触发采集，未初始化不能显示“0 只合格” |
| 无可行满仓方案 | 显示未配金额与冲突约束，允许查看测算，不出现“配置完成/全部达标” |
| 已采纳未执行 / 部分执行 | 显示已完成金额、剩余金额及是否需重核，避免整笔重复执行 |
| 加载、单源失败及恢复 | 仅当前分区显示骨架或错误，已成功内容不被全屏清空；保留数据日及重试入口 |
| 后端拒绝或请求结果不明 | 保留表单与证据，显示服务端具体原因；按幂等键查询或重试，不凭前端猜测重复创建 |

所有取消路径，包括关闭、Esc、点击取消和拒绝原因表单取消，必须产生零业务写请求。当前提案组件将原生 prompt 的取消与空理由混用，改造时必须消除这一误提交风险。提交中禁用重复操作并保留明确进度；成功后定位真实返回的提案/决策 ID，相关计数同步更新。

### 9.8 消息联动与可读性

消息只产生可处理事项：证据需用户确认、可赎且不符合续持、待开放退出计划需确认、可执行替换或已采纳方案失效。日常挂零/走势提示与例行源故障留在页面和巡检摘要，不重复生成待办。到期本身不恢复为通用催办消息。

需用户补事实或最终确认时走 `POST /api/inbox/confirmations`，按稳定的持仓 lot/事项/策略建立确定性键；证据批次变化只更新现有事项，不每日另建。事实补齐后删除已处理 `inbox_items` 投影，底层证据、通知和审计保留。卡片直接定位对应分区、对象与处理动作，并能返回来源事项。

本轮按桌面 1280×900、1440×900，浅色和深色主题验收；移动端不纳入默认范围。信息文字不低于 12px，关键金额/收益/日期优先 12.5–13px 或更大；正文对比度至少 4.5:1，功能边界及图标至少 3:1。名称换行、金额右对齐并采用等宽数字，宽表只在容器内滚动，根节点不横向溢出。

一级分区使用具有当前状态的导航链接，分区内部筛选和视图切换使用语义明确的控件；键盘可完成切换、筛选、详情、确认与返回。详情关闭回到触发位置，错误信息关联对应字段，状态不能只靠颜色或 hover。实施阶段提供真实渲染与交互证据，本计划中的结构示意不算视觉验收。

## 12. 数据变更、部署与回滚

### 12.1 数据变更原则

优先复用现有表、JSON 载荷和设置表，但不预先承诺零 schema 变更。第 13 节列出的资金预留、证据版本与任务接续需要可靠持久化和唯一约束，不能为避免迁移而只保存在进程内或无约束 JSON 中。必要的新增设置、旧待采纳提案失效都必须由显式业务用例持久化，支持重复运行和审计，不靠页面 GET 写入。

若实施中发现份额映射、交易前核验或不可变策略快照必须新增表/约束，应先提交独立变更说明：原因、两库分别备份、迁移脚本、向后兼容、失败回滚及临时库演练结果，取得明确授权后再迁移。方案审批不等于允许重写既有事实记录。

### 12.2 切换步骤

1. 在临时环境完成验收，核对未完成交易、提案状态、策略映射及全部持仓证据缺口。
2. 对账本和初筛库分别做已校验备份；记录当前版本、策略设置和历史事实摘要。
3. 上线代码但保留旧激活模式，完成只读影子对照；影子不写正式业务对象。
4. 执行一次幂等切换用例，记录策略生效时间，处理旧 pending 提案及已采纳未执行复核，统一启用新策略。切换失败时整体保持原激活状态，不产生半切换。
5. 通过现有计划任务托管完成必要重启，不改安装器、触发频率或恢复外部 Watchdog。
6. 检查 `prod:status`、`run/host-state.json`、健康与初筛 API、产品/提案/评估关键 API、桌面页面、stderr 和 stop marker；复核事实摘要及不变量。

### 12.3 回滚语义

故障先停用新推荐和采纳，账本、截图入账及历史查询继续可用；不得在新策略证据不可用时静默转用旧池发出建议。必要时回退应用版本与激活配置，但保留已落库的新决策、交易和审计，禁止为回滚代码恢复整本旧账覆盖新事实。

回退版本必须已验证能读取新 JSON 字段并识别新策略；不能继续评估时显示待核，不能按旧规则强行评价新决策。因技术故障回滚不意味着重新允许低于 2.15% 的新买或续作；恢复推荐前仍需遵守用户已采用的策略或取得明确的策略变更决定。

| 激活策略与切换记录 | 账本设置或独立策略记录；包含契约版本、模式、生效时间、单调递增激活序号与操作标识 | 激活与旧 pending 处理在一个事务内；所有进程读取同一序号，不以环境变量和页面缓存各自为准 |
| 产品身份映射 | 账本侧维护与账户持仓关联的映射；公开份额原始身份留在初筛库 | 一对一、同登记多份额聚合和冲突处理；变更后旧决策仍引用旧映射快照 |
| 交易前复核事实 | 账本侧可追溯记录或现有审计机制，保存核验对象、字段、来源、时间、证据哈希、核验者与撤回关系 | 区分适用于产品的条款和适用于持仓 lot 的确认/到账事实；修改追加版本，不覆盖已被采纳决策引用的证据 |
| 配置与决策快照 | 提案 payload、决策 review_meta 等现有 JSON 可承载不可变摘要 | 定义载荷版本、必需字段、最大体积、历史缺省语义与校验；高频查询/唯一约束不依赖全量 JSON 扫描 |
| 待执行资金预留 | 账本侧明确的意图状态，可复用已有提案/交易记录或新增预留表 | 一份有效预留只属于一个提案/决策及交易腿，唯一键、金额边界、状态转换需可验证 |
| 后台派生任务 | 可扩展现有 automation_jobs，保存事件键、策略序号、输入指纹、尝试次数及完成结果 | 初筛发布事件、账户变化和切换后的重算可恢复；现有队列表达不了租约/状态时，提出最小迁移方案 |
| 评估与复盘 | 现有 evaluation_runs、review_drafts 等记录 | 冻结评价契约和预测版本；同阶段不同策略不共用结果，已确认的月/季总结不因新规则重写 |

阶段 0 交付字段字典、状态转换表、唯一键/索引方案与实际 schema 对照。新增表还是扩展已有表依据持久化和并发需求决定；确需变更时按第 12 节另行授权，不把本节表格当成已批准 DDL。

资金预留建议在“采纳提案”时产生，生成草稿不占款；确认成交后转为实际承诺或持仓占用，拒绝/合法取消/失效时释放未执行部分。部分执行只释放或重算余额。预留与 pending 买入、切换腿代表同一笔资金时只计一次，采纳事务应在统一可分配余额上校验，两个并发提案不能各自使用同一笔余额。实际已发生交易仍按事实入账，超出预留记偏差，不丢弃事实。

持仓期限、起购、资产和费用等核验字段分别定义有效性：近期业绩/净值沿用 7 日门槛；额度需有执行时点复核；正式条款依据文件版本及变更公告；定期报告保留报告期与是否最新。不能将所有证据统一设为 7 日有效或长期有效。

### 13.2 事件接续与跨库一致性

初筛发布与账本重算分属两库，不能假设同时提交。建议复用已有任务机制实现“可重复扫描、至少一次处理、幂等落地”：

1. 初筛库先完整提交并推进已发布指针；随后可通知账本重算，但通知丢失不影响初筛发布事实。
2. 启动和周期检查将最新可用批次/持仓证据指纹与账本已处理水位对比，补建缺失的派生任务。主键须包含初筛库代次或输入内容哈希，不能只用可能在恢复后重复的 run_id。
3. 以“事件类型＋策略激活序号＋输入指纹”幂等执行。账本派生结果与任务成功/水位在账本同一事务提交；失败时不提前推进水位。
4. 持仓、交易、资金、复核事实、分配设置和策略激活变化也使相关派生结果失效，不只监听中午初筛。重复事件可合并，已采纳快照不能被重算覆盖。
5. 历史批次可用于研究回放；生产只重算最新有效上下文，不重放停机期间每个批次制造一串旧提案和消息。历史评估的确切期间仍按原规则补齐。

新库恢复到较旧备份时，核对库身份、内容指纹和处理水位；缺失证据不能靠账本水位假定存在。账本已保存的决策副本继续可查，新推荐等待核验。两库分别备份，记录共同逻辑检查点、schema/策略版本与证据文件清单，不要求跨库原子备份；恢复后必须做引用核对和派生重建。

### 13.3 定时任务职责与依赖

已核对本机 `r2`、`r2-2`、`r2-3`、`r2-4` 的实际任务定义及相关服务端调度源码。下表描述当前职责和拟改造范围，不调整现有频率，不新建 Codex 定时任务。

| 执行者 | 当前节奏/职责 | 整合后必须补充 |

金融日期分别定义为：业务日、数据披露日、确认日、赎回申请日、交易确认日和资金到账日。定时采集/巡检的工作日闸门、净值估值日历及具体产品申赎日历不能混用；短持有期遇周末或节假日要按正式条款推算可用日，不能简单相加自然日。

### 13.4 worker、并发与策略切换

当前 `automation-runner.js` 将账本路径等参数传给 `automation-worker.js`，worker 重新打开 repository 并执行 runCycle，尚无本轮所需的完整新证据契约。只给 HTTP service 注入初筛适配器不足以覆盖此链路。

实施需让 HTTP、手动评估、定时 worker、启动投影和 CLI 使用同一用例与版本解释器。建议由 worker 在事务外读取有界、已发布的证据摘要，或接收可校验的冻结摘要；实际方案要显式传递库路径/身份、策略序号及输入指纹，不在 worker 中重新启用初筛调度、默认导入旧 CSV 或执行隐式迁移。

- 进程内 `running` 标记只防本实例重入，不能替代数据库唯一键和并发控制。主线程、worker、手动 API 及 CLI 必须通过同一幂等与条件更新规则落地。
- 网络和长净值计算在事务外；SQLite 短写事务内重新核对策略激活序号、资金/持仓与复核事实版本。输入变化时返回待重算，不拿旧余额直接采纳。WAL、busy_timeout 和退避要针对写锁竞争验证，不靠放大 HTTP 超时掩盖长事务。
- 当前评估存储已在基础 dedupe_key 后追加 rule_version；问题在于该版本取自当前全局设置。新实现应使用决策冻结的评价契约及预测版本，并区分新评价、待确认结果刷新和历史已确认结果，不能笼统认为现有评估完全没有版本去重。
- 策略切换前暂停新派生写入和采纳、等待/终止在途 worker；一次事务切换激活序号、处理旧 pending 和写入切换审计。迟到 worker 提交时检查旧序号并拒绝写入。重启后按实际激活状态接续。
- 核对 runCycle 中的旧策略补齐、日开策略迁移和交易补建决策逻辑；历史修复必须限制对象范围，不能把新策略或旧历史证据自动重标为当前策略。已关闭的自动评估不得被启动补跑重新开启。
- worker 硬超时或异常退出后，保留可恢复的任务状态；落库成功但响应丢失时按幂等结果返回，不能再生成一份正式决策或重复释放资金。

### 13.5 运维、容量与隐私

健康检查分开反映“进程在线”“公开来源可用”“最新证据有效”“派生水位追上”“新策略可推荐”。主健康正常不能直接推断策略可用。状态接口应给出当前策略序号、输入批次/指纹、最后成功处理时间、积压数、尝试数、失败原因和下次重试，输出投影摘要。

记录每轮取证/计算/提交耗时、候选及阻断原因分布、SQLite 写锁等待、未配金额、事件积压和退出计划待核数量；日志使用任务、批次、决策等关联 ID。监控异常进入运维状态和既有摘要渠道，需用户处理的业务例外才写消息中心。

原始净值不重复塞进每张提案，使用哈希和必要摘要；为详情、历史评估和任务记录提供分页与必要索引，先量测再设容量阈值。初筛证据、决策快照、日志和备份分别制定保留规则；被决策引用的证据不随普通缓存清理删除，首版不自动清理历史证据。在线备份使用 SQLite 备份机制，不复制活动数据库主文件冒充完整备份。

新增复核文件纳入账本备份、哈希校验和恢复演练；文件写入与数据库引用采用暂存、提交及失败残留回收的明确协议。只接受受控文件根和已授权公开来源，避免任意路径读取；请求签名、账户证据、SQLite、任务日志和缓存不进入公开 Pages 或 Git 产物。新写接口沿用 origin/输入校验，不能只靠按钮禁用保护。

### 13.6 新增交付闸门

原第 11 节之外，增加以下必须通过的临时环境演练：

| 专项 | 必测结果 |
| --- | --- |
| 资金预留竞争 | 两个提案同时采纳不超额；部分执行、取消、失败恢复后金额守恒且不重复释放 |
| 发布通知丢失 | 初筛已发布、账本尚未建任务时退出；重启后按水位补处理一次，不漏新状态 |
| 跨库与证据恢复 | 两库恢复到不同检查点、run_id 重复或证据文件缺失时能识别，旧决策仍可解释，新推荐不能误放行 |
| worker 一致性 | 相同冻结输入经 HTTP、定时、手动与 CLI 得到同一策略结论；无旧池或默认参数回流 |
| 切换竞争 | 旧 worker 在策略切换后迟到、任务中途重启或切换失败，均无半切换和旧序号写入 |

| 性能与隔离 | 受控较大净值/历史样本下记录延迟、写锁和载荷体积；后台采集超时不阻断账本事实录入 |
