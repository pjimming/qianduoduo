# DSH 定时任务（方案 B：专用会话 + 每轮新子代理）

在 DSH 桌面端复刻 Codex 的 5 个定时任务。每条任务都在一个**专用会话**里触发，由该会话派发一个**全新子代理**执行业务文档；外层会话只做派发和汇总，不承载业务上下文。

## 为什么这样做

DSH 原生定时任务（`schedule_create`）是**会话级提醒**：任务绑定创建它的会话，到点向该会话追加一条提醒消息。它不支持「每次新会话运行」，也没有暂停态。用「专用会话 + 每轮新 `subagent`」可以在不改 DSH 的前提下得到接近 Codex 的效果：

- 子代理上下文全新，不继承会话历史，等价于 Codex 的独立 run；
- 外层会话只留「触发 + 150 字摘要」，长期不会膨胀；
- 业务产出照旧写入工作区、调用本地服务，不依赖 Codex 桌面端。

代价：DSH 桌面端必须在运行；关闭期间不会执行，重开后只补最近一次漏触发；提醒激活期间该会话不能归档。

## 打开 DSH 时的补跑

Host 启动时会扫描所有 `scheduledAt <= now` 的活动提醒，恢复绑定的冷会话并投递，不需要先点进那个会话：

- 周期任务只补「最近一次」漏掉的 occurrence；例如关了两天，只跑最近一趟，然后把下次时间推进到未来。
- 同一会话里多条同时逾期会合并成一条批提醒（每条原 prompt 都在），代理一轮里可能派发多个子代理。不想合并就一个任务一个专用会话。
- 投递成功即视为该轮到点；业务子代理失败、或投递后立刻关掉 DSH，都不会自动重试，要等下一次触发或下次开机。
- 桌面端没启动就不会补跑；会话被归档会连同提醒一起删除。

## 自检

创建后执行 `schedule_list`，应返回 5 条 `kind=cron`、`timeZone=Asia/Shanghai` 的活动任务，cron 与上表一致。把 5 个 id 回报给用户，便于后续修改或删除。

## 与 Codex 并存

两层同时启用会重复执行（重复发卡、重复发布、重复提交）。启用本方案前，先在 Codex 侧停用同名任务，或只保留一边。本方案不自动修改 Codex 任务定义。

当前（2026-11-04）：Codex 侧 5 条已全部 `PAUSED`，DSH 侧 5 条 `active`，冲突已解除。

## 维护

- 改时间或文案：`schedule_update`（仅活动任务可改）。
- 暂停：DSH 没有暂停态，只能 `schedule_delete`；恢复需按本文件重建。
- 删除或归档会话前先删提醒；会话归档会连同提醒一起失效。
- 若某轮子代理失败，下一次触发仍会照常执行；不要在外层会话里补跑写操作。
